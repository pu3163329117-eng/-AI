## 分工

主开发流程拥有架构、任务拆分、资料选择、领域规则、测试和最终验收。Harness 只接收一个任务的最小版本化上下文，返回候选审查、测试建议、文档草稿或其他只读意见。Bridge 负责身份、队列、独占运行时、状态、预算、恢复和审计；它不判定教师认证，也不写学习状态。

学生端 `DeepSeekProvider` 与协作助手完全分开。前者的最小理由反馈许可不覆盖源码、完整项目资料、数据库或本聊天历史；不得共用配额、状态表或审核结论。

## 推荐流程

1. 建立任务，明确 objective、验收条件、禁止事项和最大上下文字节数。
2. 只选任务所需的非敏感片段，为每段写 source/version/classification；不要用路径标识暗示 Bridge 自行读取文件。
3. 记录返回的 manifest id、版本和 SHA-256，再用幂等键派发 run。
4. 通过 run 或 SSE 读取状态。`harness_message_id` 仅代表入队，不能作为完成或费用结算证明。
5. 同任务追问走 messages 接口；新资料先创建 manifest 新版。旧成果会标记需复核。
6. 核对候选结果中的来源、未完成项、实际验证和风险；未运行的测试不能补写成通过。
7. 若需要应用代码或内容变更，另走现有评审/领域流程。本阶段 Bridge 没有发布或学习库写入能力。

## 任务包最低字段

- task/project/run 标识及 manifest 版本；
- 目的、验收条件、禁止事项；
- 输入来源 ID、版本、分类、截断状态与授权范围；
- 单次输出 token、运行时限及真实调用预算授权状态；
- 允许的成果格式和人工核验命令；
- 出错时是否可重试。对 `OUTCOME_UNKNOWN` 必须写明禁止自动重试。

## 返回包最低字段

- run id、runtime、Harness session/message 标识；
- 输入 manifest id/version 与是否需要重新核对；
- 候选结果、来源引用、限制和风险；
- 实际发生的状态事件与诊断码；
- 未完成项；
- 明确的 `CANDIDATE/WAITING_REVIEW` 状态。
